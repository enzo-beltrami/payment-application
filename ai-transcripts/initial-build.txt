     Plan: Hexagonal Architecture — Payment Application

     Context

     The challenge requires a payment API (create + list with encrypted card
     numbers) and a resilient dynamic webhook system. The user wants hexagonal
     architecture, DTOs with validation, and the transactional outbox pattern
     for webhooks to prevent dual-write errors (payment saved but notification
     lost, or notification queued but payment rolled back).

     The project is currently a bare Spring Boot 4.0.6 / Java 21 / Gradle
     skeleton. PostgreSQL runs via Docker Compose. Lombok and SpringDoc OpenAPI
     are already in build.gradle.kts.

     ---
     Package Structure

      WebhookTransactionStatus

     ---
     Outbox Pattern Flow

     POST /api/payments
            │
            ▼
       PaymentService.createPayment()  ◄── @Transactional
     ──────────────────────┐
            │  1. Save Payment
        │
            │  2. For each Webhook → save WebhookTransaction(PENDING)
       │
            └─── Both writes in ONE transaction (atomic)
     ────────────────────────┘
            │
            ▼
      Response returned to client immediately

            ┌── every 30 s ──┐
            ▼                │
       WebhookDeliveryScheduler
            │
            ▼
       WebhookDeliveryService.processPendingWebhooks()
            │  Load PENDING transactions where nextRetryAt <= now
            │  For each:
            │    success → status = DELIVERED
            │    failure → attempts++, nextRetryAt = exponential backoff
            │    attempts >= MAX (5) → status = FAILED
            ▼
       WebhookHttpAdapter.notify(url, PaymentEvent)  →  external endpoint

     No @Async needed — delivery is fully decoupled via the outbox table.

     ---
     Card Number Strategy

     Never decrypt on read. The raw card number exists in memory only during
     creation.

     - DB stores two columns: card_number (AES-256-CBC encrypted) and
     last_four_digits (plain text)
     - Payment domain model carries lastFourDigits (always) and cardNumber
     (nullable — only populated from the CreatePaymentCommand)
     - getMaskedCardNumber() → "**** **** **** " + lastFourDigits
     - CardEncryptionService exposes only encrypt(). No decrypt path exists in
     production code.

     ---
     Key Design Decisions

     1. Outbox atomicity — PaymentService.createPayment() is @Transactional.
     Payment row + webhook_transaction rows are written together. If anything
     fails, both roll back. The scheduler only sees committed records,
     eliminating dual-write risk.
     2. Encrypt-only — CardEncryptionService has no decrypt(). lastFourDigits is
      the only display data loaded from DB. This limits blast radius if the DB
     is compromised.
     3. WebhookTransaction.webhookUrl is denormalized — stored at creation time
     so delivery still works even if the webhook registration is later changed
     or deleted.
     4. Backoff formula — nextRetryAt = now + 2^attempts * 30s (30s, 60s, 120s,
     240s). After 5 failures → FAILED (no further delivery attempts).
     5. Single-instance assumption — no SELECT FOR UPDATE SKIP LOCKED guard
     against concurrent schedulers. Acceptable for this scope; noted as a
     limitation.
